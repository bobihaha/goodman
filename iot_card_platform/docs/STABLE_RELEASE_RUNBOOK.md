# 稳定上线操作手册

## 1. 目的

本手册用于指导物联网卡管理平台在“新增功能”后的稳定上线，目标是：

- 降低因代码、配置、SQL 变更导致的线上故障
- 固定上线步骤，减少临场操作失误
- 保证出现问题时可以快速回滚

适用项目：

- 后端：FastAPI
- 前端：Vue 3 + Vite
- 部署：Docker Compose
- 当前生产编排文件：`docker-compose.yml`

---

## 2. 当前项目上线特点

结合当前仓库，发布链路有几个关键点：

- 当前生产机器由 `docker-compose.yml` 管理，核心服务包括 `app`、`frontend`、`mysql`、`redis`
- 项目已提供健康检查脚本：`deploy/scripts/health_check.sh`
- 项目已提供数据库备份与恢复脚本：
  - `deploy/scripts/backup_mysql.sh`
  - `deploy/scripts/restore_mysql.sh`
- 数据库变更目前主要通过 SQL 文件和脚本执行，没有完整的迁移平台统一管理
- 测试存在，但不是全链路自动化，因此上线前必须做“人工卡点”

结论：

> 这个项目要稳定上线，核心不是“把代码传上去”，而是固定执行“评审 -> 测试 -> 备份 -> 发布 -> 验证 -> 观察 -> 回滚预案”。

---

## 3. 上线分级

后续每个新功能上线前，先判断变更级别。

### A 级：低风险发布

满足以下条件：

- 只改前端展示
- 只改文案、样式、非核心查询逻辑
- 不涉及数据库结构变更
- 不影响登录、权限、卡管理、库存、同步任务

处理方式：

- 可按标准流程简化执行
- 仍然必须做备份、健康检查、功能验证

### B 级：中风险发布

满足以下任一条件：

- 修改后端接口逻辑
- 修改权限、菜单、租户隔离、筛选逻辑
- 修改定时任务、同步逻辑
- 修改库存、流量池、停复机等核心流程

处理方式：

- 必须走完整标准流程
- 必须安排上线观察期

### C 级：高风险发布

满足以下任一条件：

- 有数据库结构变更
- 有历史数据修复或批量数据写入
- 有登录、鉴权、菜单权限、超级登录相关改动
- 有外部供应商接口、同步任务、扣费或状态变更逻辑调整

处理方式：

- 必须先在预发布或测试环境演练
- 必须准备明确回滚方案
- 最好选择低峰时段上线

---

## 4. 标准上线流程

以下流程默认所有功能上线都执行，A 级可以裁剪，B/C 级不要省略。

### Step 1：功能冻结

上线前先冻结本次发版范围。

要求：

- 明确本次上线功能列表
- 明确不在本次上线范围内的内容
- 禁止在上线前临时夹带新需求
- 为本次发布创建独立分支或明确 commit 范围

建议输出：

- 发布说明
- 影响模块清单
- 是否涉及 SQL、配置、定时任务、外部接口

### Step 2：变更评审

上线前至少过一遍下面 6 项：

- 改了哪些接口
- 改了哪些页面
- 是否新增环境变量
- 是否新增 SQL
- 是否修改权限与菜单
- 是否影响已有历史数据

必须重点确认的风险点：

- 多租户数据是否仍然隔离
- 列表筛选、导出、批量操作是否会串数据
- 权限收口后，旧角色是否还能正常使用
- 定时任务是否会重复执行
- 新增字段是否兼容旧数据

### Step 3：本地自测

后端和前端先在本地通过基础验证。

参考命令：

```bash
# 后端依赖
pip install -r requirements.txt

# 后端测试
pytest tests

# 前端依赖
cd frontend
npm install

# 前端构建校验
npm run build
```

最低通过标准：

- 新功能主流程跑通
- 旧功能核心路径未受影响
- 前端能正常构建
- 后端测试无明显失败

### Step 4：数据库变更评审

如果本次发布涉及 SQL，必须单独评审。

检查项：

- 是否仅新增字段，还是会修改/删除字段
- 是否涉及索引变更
- 是否涉及历史数据回填
- SQL 是否可重复执行
- SQL 执行失败后是否会留下半成品

当前项目建议做法：

- 将本次 SQL 放入单独文件，命名清晰，例如：
  - `app/db/migrations/20260319_add_xxx.sql`
- 先在测试环境执行
- 如需执行 SQL 脚本，可使用：

```bash
python scripts/run_migration.py app/db/migrations/xxx.sql
```

注意：

- 禁止上线现场临时手写 SQL
- 禁止未备份数据库就执行结构变更
- 对删除字段、删数据、批量更新数据的 SQL，必须先准备回滚方案

### Step 5：预发布验证

推荐所有 B/C 级发布都先演练一遍。

演练重点：

- 新增功能主流程
- 登录与权限
- 菜单可见性
- 核心列表查询
- 新增/编辑/删除/批量操作
- 与供应商同步或定时任务相关流程

如果预发布环境没有完全建立，至少做到：

- 在本地用生产配置镜像构建一次
- 用当前生产编排文件在测试机器拉起验证

参考命令：

```bash
docker compose build
docker compose up -d
```

### Step 6：上线前检查清单

正式上线前，逐项确认：

- 代码已合并到待发布版本
- 发布范围已冻结
- `.env.production` 是否需要变更已确认
- SQL 文件已准备好
- 回滚方案已写清楚
- 数据库备份脚本可正常执行
- 发布负责人、验证负责人已明确
- 选择了低峰时间窗口

建议至少两个人协作：

- 一人负责执行发布
- 一人负责业务验证和观察日志

### Step 7：数据库备份

正式发布前，先备份数据库。

执行命令：

```bash
bash deploy/scripts/backup_mysql.sh
```

备份要求：

- 记录备份文件路径
- 确认备份文件已生成
- 高风险发布时，备份文件保留到发布观察期结束

### Step 8：执行发布

#### 场景 1：仅代码发布，无 SQL 变更

```bash
docker compose build
docker compose up -d
```

#### 场景 2：代码发布 + SQL 变更

推荐顺序：

1. 先备份数据库
2. 执行兼容型 SQL
3. 再发布应用
4. 做上线验证

执行示例：

```bash
python scripts/run_migration.py app/db/migrations/xxx.sql
docker compose build
docker compose up -d
```

兼容原则：

- 优先“先加后用”，不要“先删后发”
- 新代码依赖的新字段，应先加字段，再发代码
- 旧字段不要在同一次发布中立即删除

### Step 9：上线后健康检查

发布完成后立即执行健康检查：

```bash
bash deploy/scripts/health_check.sh
```

该脚本会检查：

- 容器状态
- 后端 `/health`
- Nginx 首页访问
- MySQL 连通性
- Redis 连通性
- 最近后端日志

如果脚本失败，本次发布不能算完成，必须继续排查。

### Step 10：业务验收

健康检查通过后，做业务验证。

建议至少验证以下项目：

- 登录正常
- 首页正常
- 新功能主流程正常
- 相关旧功能未回归
- 权限账号访问正常
- 列表查询、筛选、详情正常
- 新增/编辑/批量操作正常

高风险模块额外验证：

- 卡状态变更
- 出入库记录
- 流量池分组与统计
- 停复机流程
- 同步任务是否异常触发

### Step 11：观察期

上线后至少保留 30 到 60 分钟观察。

重点观察：

- `docker compose ps`
- `docker logs iot_card_app --tail 200`
- `docker logs iot_card_frontend --tail 200`
- 接口报错率
- 页面白屏、慢查询、超时
- 定时任务是否异常执行

发布完成标准：

- 健康检查通过
- 业务验收通过
- 观察期内无持续报错

## 5. 回滚操作手册

### 5.1 触发回滚的条件

满足以下任一情况，优先考虑回滚：

- 登录异常
- 首页或核心页面不可用
- 核心接口大面积报错
- 权限错乱或越权
- 数据写错、批量写错
- 同步任务异常导致持续写入错误数据

### 5.2 回滚优先级

优先顺序如下：

1. 先止血
2. 再恢复服务
3. 最后分析原因

常见止血方式：

- 回滚到上一版镜像或代码
- 暂停定时任务
- 屏蔽入口按钮或菜单
- 暂停执行问题 SQL

### 5.3 代码回滚

如果是纯代码问题，优先回滚应用版本。

原则：

- 不要先动数据库
- 先恢复服务可用性
- 确保回滚后的代码兼容当前数据库结构

### 5.4 数据库回滚

如果 SQL 或数据修复导致问题，再考虑数据库恢复。

恢复命令：

```bash
bash deploy/scripts/restore_mysql.sh ./backups/mysql/xxx.sql.gz
```

注意：

- 恢复数据库前必须先停业务写入
- 恢复前先确认备份时间点
- 恢复后重新执行健康检查与业务验收

## 6. 发布 Checklist

每次上线前，可以直接照着打勾。

### 发布前

- [ ] 本次发布范围已冻结
- [ ] 功能清单和影响范围已确认
- [ ] 代码已完成评审
- [ ] 本地测试通过
- [ ] 前端构建通过
- [ ] SQL 已评审并测试
- [ ] `.env.production` 变更已确认
- [ ] 回滚方案已准备
- [ ] 发布时间窗口已确认

### 发布中

- [ ] 已执行数据库备份
- [ ] 已执行 SQL 变更（如有）
- [ ] 已重新构建并拉起容器
- [ ] 已执行健康检查脚本

### 发布后

- [ ] 已完成核心业务验证
- [ ] 已观察日志 30 到 60 分钟
- [ ] 无持续报错
- [ ] 已记录本次发布时间、版本、执行人

## 7. 团队协作要求

为了让后续新增功能能长期稳定上线，建议形成以下制度。

### 7.1 一个功能必须同时具备 4 份信息

- 功能说明
- 影响模块
- SQL 说明
- 回滚说明

没有这 4 项，不允许直接上线。

### 7.2 禁止几类高风险行为

- 禁止直接在生产库手工改表又不留记录
- 禁止边上线边改需求
- 禁止没有备份就执行 SQL
- 禁止上线后无人观察
- 禁止把多个高风险改动打包一起发

### 7.3 推荐建立发布单模板

每次发布至少记录：

- 发布时间
- 发布人
- 发布内容
- 影响模块
- 是否含 SQL
- 备份文件名
- 验证结果
- 是否回滚

## 8. 对当前项目的进一步建议

如果希望“后续新增功能上线更稳”，建议按优先级继续补下面几项。

### P1：建立统一数据库迁移机制

当前 SQL 主要靠文件和脚本执行，短期可用，长期容易漏执行、重复执行、难追踪。

建议：

- 引入统一迁移方案
- 每次结构变更必须通过迁移文件落库
- 记录版本号和执行历史

### P1：补齐自动化测试门禁

建议把以下检查做成发版前固定动作：

- 后端 `pytest`
- 前端 `npm run build`
- 核心接口 smoke test

### P1：建立预发布环境

至少保留一套接近生产的环境，用于验证：

- 配置差异
- Docker 镜像构建
- SQL 兼容性
- 权限和菜单问题

### P2：建立版本化发布

建议每次发布都打版本号，例如：

- `v2026.03.19.1`
- `v2026.03.19.2`

这样更方便回滚和追踪。

### P2：建立上线后监控

至少要能快速看到：

- 5xx 错误
- 登录失败率
- 慢接口
- 定时任务异常
- 同步失败日志

---

## 9. 一句话流程

后续每次新增功能上线，请按这一句执行：

> 先冻结范围，再评审代码和 SQL，本地自测与预发布验证通过后，先备份数据库，再执行发布，发布后立刻跑健康检查和业务验收，最后观察日志，异常立即回滚。

---

## 10. 推荐执行命令速查

```bash
# 1. 后端测试
pytest tests

# 2. 前端构建
cd frontend && npm run build

# 3. 生产镜像构建
docker compose build

# 4. 启动生产容器
docker compose up -d

# 5. 数据库备份
bash deploy/scripts/backup_mysql.sh

# 6. 执行 SQL 迁移
python scripts/run_migration.py app/db/migrations/xxx.sql

# 7. 上线后健康检查
bash deploy/scripts/health_check.sh

# 8. 必要时恢复数据库
bash deploy/scripts/restore_mysql.sh ./backups/mysql/xxx.sql.gz
```

# 数据库迁移 SOP

这份 SOP 用于生产环境数据库迁移，目标是降低手写 SQL 带来的失败风险。

## 适用范围

- 新表创建
- 字段新增
- 索引新增
- 历史数据修复
- 结构兼容性发布

不建议直接用于高风险操作：

- 大表字段类型修改
- 大表直接删列
- 高峰期大范围回填

## 迁移原则

1. 先兼容，后清理
2. 先预发，后生产
3. 先备份，后执行
4. 先结构，后数据
5. 回滚优先应用回滚，不依赖 DDL 强回退

## 标准流程

### 阶段 1：梳理变更

发布前先输出一份迁移清单：

- 本次新增哪些表
- 本次新增哪些字段
- 本次新增哪些索引
- 本次是否涉及历史数据修复
- 本次是否涉及删除字段或修改字段类型

如果涉及删字段、改类型、重建索引，默认视为高风险变更，需要单独窗口期执行。

### 阶段 2：准备迁移脚本

每次发布单独建目录，例如：

```text
deploy/migrations/2026-03-17-release/
```

目录内建议包含：

- `001_schema.sql`
- `002_data_fix.sql`
- `003_verify.sql`
- `rollback_notes.md`

要求：

- 一个文件只做一类事情
- 文件命名按顺序编号
- 不能把历史无关脚本一起混入本次发布
- 尽量使用 `IF EXISTS` / `IF NOT EXISTS`

### 阶段 3：预发演练

必须先从生产最近备份恢复出一套预发库，然后执行：

1. 跑本次迁移脚本
2. 启动新后端版本
3. 验证关键接口
4. 核对核心表记录数
5. 检查慢 SQL 和锁等待

关键核对建议：

- `sys_users`
- `iot_cards`
- `traffic_pools`
- `stock_in_records`
- `stock_out_records`
- 新增或变更表

### 阶段 4：生产前备份

生产执行前必须完成：

- RDS 自动备份点确认
- 手动快照或逻辑备份
- 导出关键表结构

至少保留：

- 迁移前表结构
- 迁移 SQL 原文
- 应用发布包版本号

### 阶段 5：生产执行

建议在低峰期按顺序执行：

1. 开启维护窗口
2. 暂停非必要后台任务
3. 执行结构迁移
4. 执行数据修复脚本
5. 执行校验 SQL
6. 发布后端
7. 执行业务冒烟
8. 发布前端

### 阶段 6：观察期

上线后至少观察 30 到 60 分钟：

- 错误日志
- 接口耗时
- 数据库 CPU / 连接数 / 锁等待
- 定时同步任务是否重复执行

## 风险分级

### 低风险

- 建新表
- 新增可空字段
- 新增普通索引

### 中风险

- 回填历史数据
- 新增唯一索引
- 修改默认值

### 高风险

- 删字段
- 改字段类型
- 改唯一约束
- 大表全表更新

## 本项目特别要求

### 1. 不要直接复用仓库里所有旧 SQL

仓库已有 SQL 和迁移脚本较多，其中部分脚本不是严格幂等，甚至存在重复内容。生产上线时只能使用“本次发布确认过”的迁移包。

### 2. 避免一步到位删旧字段

推荐采用两次发布：

第一次发布：

- 加新字段
- 回填数据
- 应用代码切到新字段

第二次发布：

- 观察稳定后删除旧字段

### 3. 新增唯一约束前必须先查脏数据

例如增加唯一索引前，必须先跑重复数据检查 SQL，并先清理冲突数据。

### 4. 大表回填要分批

不要在单条 SQL 里更新整张大表。应按主键范围或时间范围分批执行。

## 回滚策略

### 应用回滚

优先回滚应用版本，前提是数据库结构仍兼容旧版本。

### 数据回滚

仅在以下场景考虑：

- 本次只做了可逆的小范围数据修复
- 有明确回滚 SQL
- 已在预发验证过

### 结构回滚

DDL 回滚风险高，尤其是删列、索引和字段类型修改。除非已经演练，不要在生产现场临时写回滚 SQL。

## 发布检查清单

- 已确认本次迁移清单
- 已在预发库完整演练
- 已确认备份可用
- 已确认执行人和回滚负责人
- 已确认维护窗口
- 已确认后端版本和前端版本匹配
- 已确认迁移后校验 SQL
- 已确认上线后观察指标

# AI 协作开发说明

## 1. 目标

这份说明用于约束 AI 按当前项目的真实结构来写代码、写 SQL、写发布方案，减少不必要的报错和返工。

适用范围：

- 新增后端接口
- 修改前端页面
- 调整权限与菜单
- 编写 MySQL SQL
- 生成发布步骤

---

## 2. 先告诉 AI 的固定背景

以后你每次让 AI 干活，最好先把下面这段固定背景贴进去。

```md
这是一个物联网卡管理平台项目，请按当前仓库实际结构工作，不要自己假设技术栈。

项目技术栈：
- 前端：Vue 3 + TypeScript + Vite + Element Plus
- 后端：FastAPI + SQLAlchemy
- 数据库：MySQL
- 部署：Docker Compose

项目约束：
- 后端代码在 `app/`
- 前端代码在 `frontend/`
- 生产编排文件是 `docker-compose.prod.yml`
- 健康检查脚本是 `deploy/scripts/health_check.sh`
- 数据库备份脚本是 `deploy/scripts/backup_mysql.sh`
- 数据库恢复脚本是 `deploy/scripts/restore_mysql.sh`
- SQL 迁移脚本执行器是 `scripts/run_migration.py`

工作要求：
- 先看现有代码和目录结构，再开始写
- 不要凭空新增不存在的框架和中间件
- 修改接口时，要同时检查前端调用是否受影响
- 写 SQL 时，要兼容 MySQL，并考虑线上已有数据
- 如果有数据库变更，请单独输出 SQL 文件内容和回滚方案
- 优先做兼容性变更，避免一次发布中删字段或破坏旧逻辑
```

## 3. 你目前最稳的开发发布流程

你刚才说的流程：

> 本地写好代码 -> 测试好 -> Docker 打包到本地 -> 再发布到线上

这个方向是对的，但建议你改成下面这个更稳的版本：

1. 本地写代码
2. 本地功能自测
3. 跑后端测试
4. 跑前端构建
5. 如果有 SQL，单独写成迁移文件
6. 本地按生产方式 Docker 构建
7. 在本地或测试机拉起容器验证
8. 备份线上 MySQL
9. 先执行兼容 SQL
10. 再发布线上容器
11. 发布后健康检查与业务验收

也就是说：

> 不要只“本地 Docker build 成功”就直接上生产，最好至少再做一次容器启动验证。

## 4. 让 AI 写代码时的提问方式

### 4.1 新增功能的标准提问模板

```md
请按当前项目结构实现这个功能，不要脱离现有代码风格。

功能目标：
[在这里写清楚要做什么]

影响范围：
- 前端页面：
- 后端接口：
- 数据库表：
- 权限/菜单：

开发要求：
- 先阅读相关代码再修改
- 优先复用现有 service/crud/schema/api 结构
- 不要擅自重构无关模块
- 如果涉及数据库变更，请单独提供 MySQL SQL
- 如果涉及接口字段变化，请同步检查前端调用
- 完成后告诉我：
  1. 修改了哪些文件
  2. 是否需要执行 SQL
  3. 如何测试
  4. 发布风险点
```

### 4.2 修 Bug 的标准提问模板

```md
请按当前项目代码结构修复这个问题，先定位原因，再改代码。

问题现象：
[写清楚报错、页面表现、接口异常]

相关模块：
[例如库存、流量池、用户、权限]

修复要求：
- 先找根因，不要只改表面
- 不要影响已有功能
- 如果要改 SQL，请单独输出 SQL 文件
- 修复后告诉我复现原因、修改点和验证方法
```

## 5. 让 AI 写 MySQL 时的要求

这是最关键的一块。以后你让 AI 写 MySQL，一定要加下面这些约束。

### 5.1 必须告诉 AI 的规则

```md
请为 MySQL 编写 SQL，必须遵守以下规则：

- 兼容当前线上已有数据
- 优先新增，不要直接删除
- 不要直接修改已有字段含义
- 尽量使用 `IF NOT EXISTS` 思路避免重复执行报错
- 涉及批量更新时，要先给出影响范围说明
- 必须同时给出回滚 SQL 或回退方案
- 不要输出 PostgreSQL 或 SQLite 语法
- 不要假设存在 Alembic，当前项目主要通过 SQL 文件执行
```

### 5.2 推荐 AI 输出格式

让 AI 按这个格式给你：

```md
请按下面格式输出：

1. 变更目的
2. 上线前风险提示
3. 正式 SQL
4. 回滚方案
5. 执行顺序
6. 验证 SQL
```

### 5.3 一个更安全的 SQL 提问模板

```md
请根据当前项目，帮我写一份 MySQL 变更 SQL。

需求：
[写清楚新增什么字段/表/索引]

要求：
- 面向 MySQL 8
- 要考虑线上已存在历史数据
- 不能影响旧代码立即运行
- 优先做兼容性发布
- 输出正式 SQL
- 输出回滚方案
- 输出验证 SQL
- 说明这次 SQL 是否适合在发版前执行
```

## 6. AI 最容易犯错的地方

以后你可以重点防这几类错误。

### 错误 1：脱离项目真实结构乱写

表现：

- 明明是 FastAPI，AI 却写成 Flask/Django
- 明明是 Vue 3，AI 却给 React 代码
- 明明用 SQLAlchemy，AI 却乱写 ORM 方式

避免方式：

- 每次都先说明项目技术栈和目录结构
- 要求 AI 先读现有文件，再修改

### 错误 2：只改后端，不看前端调用

表现：

- 接口字段改了，前端没同步
- 参数名变了，页面直接报错

避免方式：

- 明确要求 AI 同时检查接口定义和前端调用位置

### 错误 3：SQL 不考虑线上数据

表现：

- 直接改字段类型
- 直接删字段
- 一次性覆盖历史数据
- 没有回滚方案

避免方式：

- 强制要求“兼容旧数据”
- 强制要求“先加后用”
- 强制要求“输出回滚方案”

### 错误 4：把测试环境写法当成生产发布方案

表现：

- 只给本地运行命令
- 不考虑 Docker Compose
- 不考虑数据库备份

避免方式：

- 明确告诉 AI：生产发布必须基于 `docker-compose.prod.yml`

## 7. 最推荐你的实际用法

后续你可以固定用下面 3 种方式跟 AI 协作。

### 用法 1：先让 AI 做方案

适合复杂功能。

模板：

```md
请先不要写代码，先基于当前项目分析这个功能要改哪些文件、是否要改 SQL、发布风险是什么。
```

### 用法 2：再让 AI 真正改代码

模板：

```md
请按当前项目结构直接修改代码，并告诉我改了哪些文件、怎么测试、是否需要执行 SQL。
```

### 用法 3：上线前让 AI 做发布审查

模板：

```md
这是我这次准备上线的改动，请按当前项目帮我做一次发布审查：
- 是否涉及 SQL
- 是否有高风险点
- 发布顺序是否合理
- 回滚方案是否足够
```

---

## 8. 最后给 AI 的固定要求

以后你可以长期把这段放在需求后面：

```md
请你按当前项目实际代码来做，不要凭空假设。
先读代码，再修改代码。
如果涉及 MySQL，请提供正式 SQL、回滚方案、验证 SQL。
如果涉及接口变更，请同步检查前端。
如果涉及发布，请按 `docker-compose.prod.yml`、备份脚本、健康检查脚本给出方案。
优先保证兼容性和可回滚，不要只追求一次性改完。
```
